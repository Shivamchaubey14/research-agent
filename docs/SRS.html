1  Introduction

1.1  Purpose

This document specifies the requirements for DeepResearch, an agentic artificial intelligence platform that automates the end-to-end research workflow. Given a natural-language question, the system autonomously decomposes the problem, gathers evidence from the public web and from a private document corpus, critically verifies the gathered evidence against its sources, and composes a structured, citation-backed report. The purpose of this SRS is to establish a single, unambiguous and verifiable baseline of what the system shall do and the quality attributes it shall exhibit, so that engineering, quality assurance and operations teams share a common understanding and can independently validate the delivered product.

1.2  Document Conventions

The key words shall, should and may are used in the sense defined by RFC 2119: shall denotes a mandatory requirement, should a recommendation, and may an optional capability. Requirement identifiers are stable and must not be reused if a requirement is retired.

1.3  Intended Audience

This specification is written for the following readers, each of whom is expected to consult the sections most relevant to their role:

  • Software Engineers — Sections 3–7 for architecture, interfaces, functional and data requirements that drive implementation.
  • Quality Assurance Engineers — Sections 5, 8 and 11 to derive test cases and acceptance criteria.
  • DevOps / Platform Engineers — Sections 9 and 10 for deployment topology, scaling and the delivery pipeline.
  • Product Owner & Reviewers — Sections 1, 2 and 7 for scope, vision and behavioural expectations.
  • Hiring Managers / Technical Evaluators — the document as a whole demonstrates production-grade engineering rigour applied to a modern GenAI system.

1.4  Product Scope

DeepResearch delivers a web application in which an authenticated user submits a research question and receives, in return, a streamed, transparent account of the agent's reasoning followed by a final cited report that can be saved, revisited and exported. The platform is deliberately built as a set of cooperating microservices connected by an event backbone, so that the computationally heavy and long-running agent workload scales independently of the web tier.

In Scope

  • Autonomous multi-step research with tool use
  • RAG over user-uploaded documents
  • Live streaming of agent progress
  • Source verification and inline citations
  • Persisted, browsable report history
  • JWT-secured multi-user access
  • Containerised, Kubernetes-deployable services
  • Automated CI/CD and an offline evaluation suite

Out of Scope (v1.0)

  • Real-time collaborative editing of reports
  • Fine-tuning or self-hosting of foundation models
  • Mobile-native applications
  • Payment / billing and subscription management
  • Multi-tenant organisation hierarchies
  • Languages other than English (planned, not committed)

2  Overall Description

2.1  Product Perspective

DeepResearch is a new, self-contained product rather than a component of a larger system. It is, however, deliberately decomposed into independently deployable services that communicate through well-defined contracts. The web tier (Django + DRF) owns identity, persistence and request admission; the worker tier owns the long-running agentic computation; Apache Kafka decouples the two so that a burst of submitted research questions is absorbed as a durable queue rather than overwhelming synchronous request handlers. 2.4  Operating Environment

  • Client: Any evergreen desktop browser (Chrome, Edge, Firefox, Safari) supporting ES2020 and Server-Sent Events.
  • Server: Linux containers orchestrated by Kubernetes 1.28+, or a single host via Docker Compose for development.
  • Runtime: Python 3.12 (API & worker), Node 20 build toolchain (frontend).
  • Data services: PostgreSQL 16, Redis 7, Qdrant, Apache Kafka 3.7 (KRaft).
  • External: Anthropic Claude API; a web-search provider.

2.5  Design & Implementation Constraints

  • The API shall be implemented with Django + DRF; the SPA with React (Vite).
  • Inter-service asynchronous communication shall use Kafka topics with explicit, versioned event schemas.
  • All services shall be stateless where possible and horizontally scalable; durable state lives only in Postgres, Qdrant and Redis.
  • Secrets shall never be committed; they are injected via environment variables / Kubernetes Secrets.
  • LLM access shall be confined to the worker tier to centralise cost control and prompt governance.
  • The system shall degrade gracefully when an external dependency (LLM or search) is slow or unavailable.

2.6  Assumptions & Dependencies

  • A valid Anthropic API key with sufficient quota is available to the worker tier.
  • The web-search provider's terms permit programmatic access at the expected volume.
  • Users have network connectivity adequate for an SSE stream.
  • The deployment target provides persistent volumes for stateful services.
  • Foundation-model behaviour may evolve; prompts and evals are versioned to absorb change.

3  System Architecture

3.1  Architectural Overview

DeepResearch follows an event-driven microservice architecture. The React SPA talks only to the Django API over HTTP and consumes a one-way Server-Sent Events stream for live progress. When a research run is requested, the API persists it, publishes a job event to Kafka and returns immediately — the request is never blocked on the multi-minute agent computation. One or more worker replicas consume jobs, execute the agentic loop against the Claude API and the search and retrieval tools, and publish progress and result events back through Kafka and Redis. Figure 2 shows the full topology and the path of a single request.

Why this shape. Separating the web tier from the worker tier behind Kafka is the single most important architectural decision. It lets the slow, bursty, expensive agent workload be queued durably and scaled by adding consumers, while the API stays fast and responsive. This is the same pattern used in production GenAI platforms and is the heart of the system's scalability and resilience story (Sections 8 and 9).

3.3  The Agentic Reasoning Loop

The intellectual core of the product is the worker's control loop. The agent is given the goal, a system policy and a set of tools. It iterates: it thinks and decides whether to act, invokes a tool, observes the result, and repeats until it judges it has sufficient grounded evidence — at which point it verifies its draft claims against the collected sources and synthesises the final cited report. A hard iteration ceiling and token budget guarantee termination. Figure 3 specifies the loop.

3.4  Event-Driven Messaging Model

Kafka topics form the contract between services. Topics are partitioned to allow parallel consumption; a run's identifier is used as the partition key so that all events for one run preserve order. Consumer offsets are committed only after successful processing, giving at-least-once delivery; handlers are idempotent on run_id + seq to make reprocessing safe.

TopicProducerConsumerKeyPayload
research.jobsDjango APIAgent workersrun_idQuestion, options, user, document scope.
research.eventsAgent workerStream gatewayrun_idStep type, message, partial output, timestamp.
research.resultsAgent workerDjango APIrun_idFinal report, citations, token/cost usage.
research.dlqAny consumerOps toolingrun_idFailed event + error context (dead-letter).

3.5  Retrieval-Augmented Generation Pipeline

RAG operates in two phases. Ingestion (offline, on upload): a document is parsed, split into overlapping chunks, embedded and upserted into Qdrant with metadata. Retrieval (online, during a run): the agent's sub-question is embedded, the top-k nearest chunks are fetched, optionally re-ranked, and supplied to the model as grounded context with their source references preserved for citation. 9  Deployment & Infrastructure

9.1  Containerisation

Every service ships as an immutable OCI image built from a minimal, multi-stage Dockerfile. Development uses Docker Compose to bring up the full stack on one host; production uses the same images on Kubernetes. This image parity (NFR-PORT-1) eliminates "works on my machine" drift.

9.2  Kubernetes Topology

Stateless tiers (frontend, API, worker) are Deployments with multiple replicas behind Services; ingress terminates TLS and routes by path. The worker Deployment carries a HorizontalPodAutoscaler keyed on Kafka consumer lag, so backlog drives scale-out. Stateful services (Postgres, Kafka, Qdrant, Redis) run as StatefulSets with PersistentVolumeClaims. Figure 11 shows the cluster.

9.3  Environments & Configuration

EnvironmentPurposeNotes
LocalDevelopment & debugging.Docker Compose, single host, hot reload.
StagingPre-production validation.Kubernetes namespace mirroring prod; seeded data.
ProductionLive workloads.Autoscaling, alerting, backups, restricted secrets.

All configuration is supplied through environment variables, ConfigMaps and Secrets — never baked into images — satisfying the twelve-factor configuration principle.

11.2  Agent Evaluation (GenAI-specific)

Because the agent is probabilistic, traditional assertions are insufficient. A dedicated, versioned evaluation suite scores each release against a held-out set of questions with known good answers and sources. The suite runs in CI and gates promotion.

FaithfulnessFraction of report claims supported by a cited source.Maximise

Hallucination rateFraction of claims unsupported or contradicted by evidence.Minimise
